## 1. 주석 규율 — implementer 프롬프트에 주석 억제 규칙 추가

**근거 (관측됨):** dogfood 산출물 주석 비율 31%, 상당수가 요구사항 재진술
소음. `skills/looprun/references/agent-prompts.md` 전체에 주석에 대한 규칙이
한 줄도 없음 — TDD implementer가 acceptance criteria를 주석으로 옮겨 적는
전형적 패턴이 무방비.

**수정 방향:** 템플릿 A(implementer)에 한 줄 추가. 취지: "주석은 코드가
스스로 보여줄 수 없는 제약을 적을 때만. 요구사항 재진술, 다음 줄 설명,
변경 정당화 주석 금지." 필요하면 test-integrity 렌즈(템플릿 B/D)에도
소음 주석 체크를 넣을 수 있으나, 우선 implementer 쪽 한 줄로 시작하고
다음 dogfood에서 비율이 떨어지는지 본다.

**게이트:** 없음. 가장 싸고 근거가 서 있는 항목 — 첫 번째로 처리.

**검증 (2026-07-06, toy-project 0.7.0 런):** 31% → **전체 ~6%**
(825줄 중 47줄; app.js 10.7%, 테스트 0~9.2%). app.js 잔존 주석 13줄
전수 검사 — 전부 제약형(수용된 한계, "의도된 동작" 방어, Chromium/IME
플랫폼 제약, 신뢰경계 정합). 금지 3종(요구사항 재진술·다음 줄 설명·변경
정당화) 0건 — 규칙이 소음만 걸러내고 가치 있는 주석은 남김. 캐비앳:
타 프로젝트·타 언어 단일 런이라 방향성 증거. 다음 실전 런에서 재확인
시 확정 클로즈.

## 2. 비용 진단 — 설계가 비싼가, 이번 플랜의 태그가 보수적이었나

**근거 (관측됨):** dogfood 런이 월 스펜드 리밋을 침. 단, 원 분석의
"태스크당 implementer + 3렌즈 패널"은 설계와 다름 — 3렌즈는 `heavy` 전용,
`light`는 검증자 1명 (README FAQ가 이 트레이드를 명시). 리밋을 친 원인이
설계 자체인지, 플랜 태깅인지가 아직 안 갈렸다.

**수정 전 진단 (이게 이 항목의 실제 작업):** dogfood 프로젝트의
`.loopspace/plan.md`와 `journal.md`에서 확인 —
- heavy/light 태그 비율. loopplan은 "애매하면 heavy"로 태그하게 되어 있어
  (`skills/loopplan/SKILL.md`) heavy 쏠림이 유력한 가설.
- 태스크당 평균 재시도 횟수 (재시도마다 fresh implementer + 재검증이 도니
  비용 증폭기).
- 3렌즈 패널이 돈 태스크 중 실제로 heavy했던 비율.

**수정 방향 (진단 결과에 따라 분기):**
- heavy 쏠림이 원인 → loopplan의 risk 태깅 기준을 구체화하고, plan 리뷰
  패널의 "태그 정직성" 체크에 반대 방향(과잉 heavy)도 보게 함. 현재는
  under-tagging만 감시하는 방향으로 기울어 있음.
- 재시도가 원인 → 별도 항목 아님, stall policy가 이미 다루는 영역.
- 설계 자체가 원인 → light 검증 체크리스트 경량화 검토 (단, "verify heavy"
  원칙과의 긴장을 명시하고 결정).

**게이트:** 진단 없이 프롬프트/티어를 손대지 않는다.

**진단 결과 (2026-07-06, kbo-away-fans Lane C 런):**
- 14태스크 중 heavy 6 (43%). 재시도 0·재계획 0·halt 0 — 전 태스크 첫
  시도 PASS. **재시도 증폭설 기각.**
- 디스패치 회계: 구현 14 + 검증 26(패널 6×3=18, 단독 8×1=8) + phase 2
  = 42. 검증이 62%. 스펜드 리밋 중단 2회 모두 검증 웨이브에서 발생
  (1.3 재디스패치 1회, 2.3은 오케스트레이터가 잔여 기계 체크 직접 완료).
- heavy 타당성: 1.3/1.5/2.4/2.5 타당, 1.2 경계선, **1.4는 과잉 heavy**
  (순수 Dart 도메인 함수 — security 렌즈가 볼 표면 없음). 단 1.4를
  light로 재태깅해도 절감 ~5% — 태깅 교정 효과는 부차적.
- 판정: 재시도 아님, heavy 쏠림은 부분 기여. 주요인은 (a) **월 리밋이 런
  시작 전 이미 상당 소진** — 첫 중단이 태스크 3개째(1.3)에서 발생, (b)
  설계 기저의 검증 비중(비용 핵은 heavy 패널: 검증 26 중 18). "light
  체크리스트 경량화" 분기는 부적중 — light는 이미 검증자 1명.
- 조치 (실행함): loopplan risk 기준에 "순수 인메모리 로직(I/O·신뢰경계·
  신규 의존성 없음)은 core여도 light" 추가 + plan 패널 태그 정직성
  체크를 양방향(과잉 heavy 포함)으로 확장. 티어 구조 자체는 불변경.

## 3. 구조 경제성 렌즈 — cross-task 구조 비대는 누구의 렌즈도 아니다

**근거 (관측됨):** display-only Map 화면이 7파일. 방어 장치가 이미 3겹
있는데도 뚫렸다 — spec 패널 over-engineering 렌즈
(`panel-reviewers.md:40`), plan 패널 gold-plating 감사
(`loopplan/SKILL.md:60`), implementer "minimal code to pass" + scope 제한
(`agent-prompts.md:57,61`), 검증자 scope-creep 체크 (`agent-prompts.md:153`).

**원인 분석:** 태스크 단위 scope는 모두가 지키는데, 태스크마다 자기 파일을
만들다 보니 누적되는 구조적 비대(파일 수, 간접층)는 어느 렌즈의 관할도
아님. phase verifier(템플릿 C)의 cross-task 체크도 "phase 목표 대비 범위
드리프트"만 보지 구조 경제성은 안 봄 (`agent-prompts.md:205`).

**수정 방향 (둘 중 택일 또는 조합, 착수 시 결정):**
- phase verifier에 구조 경제성 체크 추가: "이 phase가 만든 파일/간접층이
  기능 대비 과한가, 합칠 수 있는 것이 있나" — FAIL이 아니라 advisory로
  시작해 journal에 기록만 하고, 반복 관측되면 FAIL로 승격.
- 또는 상류(loopplan)에서: 태스크 분해 시 "새 파일 생성은 기존 파일 확장이
  불가능할 때만" 류의 배치 힌트를 태스크 블록에 넣게 함.

**주의:** 스펙 자체의 "과엔지니어링 금지" 원칙과 정합 — 이 수정 자체가
과엔지니어링이 되지 않게 advisory부터. 2번 진단과 같은 dogfood 저널을
보게 되므로 함께 조사하면 싸다.

**진단 겸사 관측 + 착수 (2026-07-06):** 7파일 재확인 (map_models /
map_domain / naver_map_config / map_screen / map_view / naver_map_view /
map_controller). 단 seam 2파일(map_view/naver_map_view)은 acceptance의
테스트 격리 요구가 강제한 구조 — advisory가 "요구된 격리"를 비대로
오인하면 안 됨. → 첫 번째 안(phase verifier advisory)으로 착수, 템플릿
C에 구조 경제성 체크 + `structure-note` 필드 추가(FAIL 불가·기록만),
문구에 격리-예외 반영. 반복 관측 시 FAIL 승격은 기존 게이트대로.

## 4. loopupdate 명령 — 정의부터

**근거:** 원 목록 1번. 단, 무엇을 업데이트하는 명령인지 미정의.

**갈림길:**
- **플러그인 자체 업데이트**라면: Claude Code `/plugin` (marketplace
  update)이 이미 하는 일 — 스킬로 감쌀 실익이 있는지부터 확인. 실익이
  없으면 README에 업데이트 방법 한 줄 적고 클로즈.
- **런 중 spec/plan 갱신**이라면: "spec 동결, plan은 re-plan 경로로만"
  원칙과 정면충돌. 이 방향이면 별도 설계 논의(5번과 연결됨) 없이 착수
  금지.

**게이트:** 정의가 내려질 때까지 착수하지 않는다.

**정의 확정 + 착수 (2026-07-06):** 사용자 정의 = **플러그인 자체
업데이트** (타 플러그인의 /xxx-update 류 UX). 실익 확인됨 — `claude
plugin update` CLI가 존재(restart required to apply)해서 스킬이 안내문이
아니라 실제 업데이트를 실행 가능. `skills/loopupdate` 추가: marketplace
refresh → update → 구→신 버전 사이 CHANGELOG 표시 → 런 가드
(`run_status: executing`이면 안정 지점 재시작 권고 — 런 하나가 템플릿
버전을 섞지 않게) → 재시작 안내. README Install 절에 업데이트 문단
추가. **클로즈.**

## 5. "엄격함은 spec만큼만" — 중간 인간 체크포인트 (설계 논의 항목)

**근거 (구조적, 타당):** spec이 틀리면 루프는 틀린 것을 100% 커버리지로
충실히 만든다. spec-gap halt는 *모순*은 잡지만 "틀리진 않았는데 이상한"
spec은 못 잡음. plan 승인이 마지막 human touchpoint라는 건 의도된
설계이므로, 이 항목은 버그 수정이 아니라 **트레이드오프 재협상**이다.

**수정 방향 후보 (착수 전 하나를 골라야 함):**
- phase boundary에 **선택적** 인간 체크포인트: plan 승인 시 사람이
  "phase 경계마다 확인할게" 플래그를 켤 수 있게. 기본값은 현행 무인 유지.
- 검증자/phase verifier에게 halt 권한 없는 **advisory 채널**: "spec대로
  맞긴 한데 이상하다" 소견을 journal + handoff에 적게 하고, 사람이 다음
  touchpoint(halt, 완료, 세션 교체)에서 보게 함. 무인 원칙 무손상 — 이쪽이
  운영 원칙과 더 정합.

**주의:** "무인 루프"가 loopspace의 핵심 가치. 인간 개입 지점을 늘리는
수정은 그 가치와 정면충돌하므로, advisory(무인 유지) 방향을 먼저 시도하고
그걸로 부족하다는 관측이 쌓일 때만 체크포인트로 간다.

**결정 + 착수 (2026-07-06):** 사용자 결정 = **advisory 안** (무인 루프는
계속 끌고 갈 핵심 가치). 구현: 검증자 전원(템플릿 B/C/D)에 `spec-concern`
리포트 필드 — "모순 없이 올바르게 구현됐지만 spec 설계로서 의문"인 것만,
모순·추측 요구는 여전히 implementer BLOCKED → spec-gap halt 경로.
오케스트레이터는 verbatim 저널 기록만 하고, 사람의 **읽는** 접점 두 곳에서
노출: halt report.md의 `## Spec concerns` 섹션(state-format에 선택 섹션
추가), 런 완료 리포트. 8번 advisory 패턴 재사용이라 추가 디스패치 0.
**의도적 이탈 1건(거부권 대상):** 원안의 "journal + handoff" 중 handoff는
제외 — handoff 불릿은 implementer 디스패치에 주입되는데, "spec이
수상하다"는 노트를 implementer가 보면 동결된 spec을 우회 구현하려는
압력이 됨. 어차피 모든 런은 halt 또는 complete로 끝나므로 두 리포트가
전 경로를 커버. 체크포인트(사람 개입) 승격은 기존 게이트대로 — advisory로
부족하다는 관측이 쌓일 때만.

## 6. 세션 클리어 자동화 — headless supervisor (2026-07-05 설계 논의 반영)

**근거:** 현행은 30% 임계에서 사람이 `/clear` + `/loopresume` 타이핑
(README FAQ: 하니스 제약). 원 목록 4번 — 1단계 Claude가 제어, 2단계
supervisor.

**착수 전 전제 검증 (필수):** 최근 Claude Code는 긴 컨텍스트를 자동
요약(compaction)해서 세션이 이어진다. 현재 버전에서 30% 수동 핸드오프가
**아직 실재하는 문제인지**부터 확인 — 자동 요약이 loopspace 오케스트레이터
상태(디스패치 규율, diet)를 안 깨고 런을 이어주면 인터랙티브 경로는
축소·클로즈될 수 있다. 다음 dogfood 런에서 임계 도달 시 핸드오프 없이
계속해 보는 실험이 가장 싼 검증. **단, supervisor는 compaction과 무관하게
별개 가치가 있다** — 진짜 무인 런(터미널 안 보는 밤샘 실행)은 어차피
headless + 재기동 루프가 필요.

**전제 검증 완료 (2026-07-06, toy-project simple-todo 런): compaction은
오케스트레이터 규율을 깨지 않는다.** 실험: 30% 임계 handoff 요청을 거부
("계속 진행")하고 3.1 사이클 도중 Esc 중단 + `/compact` 강제 트리거
(최불안정 지점). 요약 이후 관측 — 중단된 dispatch가 남긴 untracked
파일을 재검토·버그 수정 후 채택(3.1 저널에 명기), heavy 패널 2웨이브·
stash failed-first·저널 포맷·approach 라인·Project Facts·체크포인트
커밋 전부 규격 유지, 직접 구현·재작업 0건, phase 3 boundary까지 정상
(`a4364d9`), state.md 포인터도 boundary에서 4.1로 정상 갱신. 근거:
루프의 상태가 대화가 아니라 디스크에 살아서 요약 후 재구성이 됨.
**후속 결정 2건:**
- 인터랙티브 경로: looprun Context Threshold 규칙 완화 후보 — handoff.md
  작성(안전망)은 유지하되 `/clear` 안내를 "선택"으로 낮추는 스킬 수정.
  단일 런 증거이므로 착수는 별도 결정 (다음 실전 런에서 자연 재확인 후
  권장).
- supervisor: 범위를 무인(밤샘) 런으로 한정 — 예정대로 별개 가치 유지,
  v1 스코프 불변.

**v1 구현 완료 (2026-07-06, 0.11.0):** `scripts/supervise.sh`(POSIX sh) +
`skills/loopsupervise` 배포. 확정 결정 V1~V5 전부 반영 — sh 정본(Mac
네이티브 + Windows Git Bash), 텔레그램 env opt-in, `--dangerously-skip-permissions`
전제, 무진전 2회 가드, halt=알림+exit. looprun/loopresume/state.md 무수정
(읽기 전용 제어 계층). 인터랙티브 경로 `/clear` 필수 유지 — **인터랙티브
경로 완화 후보는 기각**(사용자 결정: /clear 안내 필수 유지). halt 답장 자동
주입은 v2.

### 기각된 안: 텔레그램으로 /clear 원격 입력

`/clear`는 모델이 받는 메시지가 아니라 CLI가 가로채는 UI 명령. 텔레그램
플러그인 메시지는 세션 안의 모델에게 사용자 발화로 전달될 뿐이라, 텔레그램
에서 `/clear`를 쳐도 컨텍스트는 안 비워진다. **텔레그램의 자리는 제어
채널이 아니라 알림/결정 채널** — "halt 했다, 옵션 골라줘" / "런 완료,
머지·PR·유지 중 선택". supervisor가 Telegram Bot API를 직접 치면 (curl
한 줄) Claude Code 플러그인 의존도 없어 하니스 중립 유지.

### 채택 방향: headless supervisor

핵심 통찰: **headless로 돌리면 "클리어"가 필요 없다.** `/clear` 댄스는
런이 인터랙티브 터미널 세션 하나에 살기 때문에 존재한다. `claude -p
"/loopresume"`는 매 호출이 새 프로세스 = 새 컨텍스트 — 프로세스 종료가
곧 클리어다.

```
loop:
  claude -p "/loopresume" 실행 → 종료 대기
  .loopspace/state.md 읽기
    executing (프로세스는 죽음) → 컨텍스트 임계 or 크래시 → 재기동
                                  (loopresume이 어차피 크래시 복구 담당)
    halted                      → 사람 호출 (텔레그램 알림) → 대기
    complete                    → 사람 호출 → 종료
```

state.md의 현행 포맷이 이 판별에 필요한 신호를 이미 다 갖고 있음 — 임계
핸드오프는 `run_status: executing` 유지 + handoff.md 작성이므로 "프로세스
사망 + executing" = 재기동으로 충분. **포맷 수정 불요.**

**정당성 (검증된 방식인가):** headless는 공식 표면이다 — 공식 문서
"Run Claude Code programmatically" (code.claude.com/docs/en/headless),
자동화 전용 플래그(`--allowedTools`, `--output-format json`), Anthropic
자체 GitHub Action도 headless로 구동. 비공식 뒷문이 아님.

**배포/UX (플러그인 사용자 동선 유지):**
- `scripts/supervise.sh`로 플러그인 repo 안에 배포 — 별도 배포물 아님,
  ~100줄. 플러그인이 실행 스크립트를 배포하는 건 이미 정상 표면
  (`hooks/session-start.sh`가 선례).
- 앞문은 `/loopsupervise` 스킬: 세션 안에서 전제조건 확인(.loopspace 존재,
  run_status, 권한 설정)까지만 하고, **딴 터미널에 붙여넣을 한 줄을 출력**.
  세션 안 nohup 자동 실행은 비추천 — 수명 관계·권한 프롬프트가 꼬임.
- supervisor는 opt-in 파워유저 경로. 일반 사용자의 기본 흐름(슬래시 명령
  + 수동 핸드오프)은 순수 플러그인 UX로 그대로 유지.
- Agent SDK로 짜는 선택지는 기각: SDK는 Claude 전용이라 7번(다중 하니스)
  과 부정합. 셸/파이썬 + CLI 명령 스왑이 중립적.

**7번과의 관계:** supervisor는 하니스 중립적인 유일한 제어 계층이 된다.
supervisor가 아는 건 실행 명령(`claude -p ...` vs `codex exec ...`, 설정
한 줄)과 `.loopspace/` 상태 파일뿐 — 하니스 교체가 launch command 스왑.
looprun 스킬 로직 포팅(7번의 진짜 리프트)과는 무관한 계층.

**가드 (구현 시 필수):**
- halt는 절대 자동 재기동 금지 — halt의 의미(사람 결정 대기)가 죽는다.
  v1은 halt 시 알림만; 사람 답장을 `claude -p "/looprun — 결정: ..."`로
  주입하는 건 v2.
- 무진전 가드: 재기동 사이 state.md 태스크 포인터 비교, N회 무진전이면
  정지 + 알림 (무한 재기동 방지).
- 권한: headless 무인 런은 `--dangerously-skip-permissions` 또는 촘촘한
  allowlist 필요 — 컨테이너/전용 머신 실행을 전제하는 게 안전.

**게이트:** 전제 검증(compaction 실험) 전 구현 금지. 구현 시 v1 범위는
supervise.sh + /loopsupervise 스킬 + halt/complete 텔레그램 알림까지.

## 8. phase boundary 태스크 재검토 — 후반 phase 분해의 신선도 문제

**근거 (구조적 추정, 아직 미관측):** plan.md는 loopplan 시점에 전체 phase의
태스크를 업프론트로 확정한다. phase 5개짜리 런이면 phase 4-5의 태스크
분해는 phase 1-3의 구현 결과(실제 파일 구조, 드러난 제약, 수정된 Project
Facts)를 전혀 못 보고 만든 것 — 뒤로 갈수록 분해가 낡는다. 현행 보정
장치는 stall tier 1 re-plan 경로뿐인데, 이건 태스크가 3번 실패해야 발동하는
사후 장치라 "낡은 분해 → 실패 3회 → 재계획"의 비용을 먼저 치른다.
태스크 내부의 spec>plan>execute(STAGED CONTRACT)는 이미 있으므로, 빈 곳은
phase 사이의 plan 신선도 검토다.

**수정 방향 (착수 시 택일):**
- phase verifier PASS 후, 다음 phase 브랜치 생성 전에 **plan 신선도 체크**를
  phase boundary 절차에 추가: fresh 서브에이전트가 다음 phase의 태스크
  블록들을 현재 코드베이스와 대조 — 이미 충족된 criteria, 존재하지 않는
  파일 참조, 선행 phase에서 드러난 제약과의 충돌을 점검. 발견 시 기존
  re-plan 경로(spec 범위 내 분할/재정렬, `## Re-plans` 추가)를 그대로 타서
  수정 — 새 plan 변경 채널을 만들지 않고 발동 시점만 앞당기는 것.
- 또는 최소형: phase boundary handoff.md에 "다음 phase 태스크 중 의심
  항목" advisory만 적게 하고, 실제 재분해는 여전히 stall 경로에 맡김.

**주의:** "plan은 re-plan 경로로만 바뀐다" 원칙(looprun Rules)과의 정합이
핵심 — 재검토가 무제한 재분해 권한이 되면 plan 승인(마지막 human
touchpoint)의 의미가 죽는다. 태스크당 re-plan 1회 제한 등 기존 한도를
공유해야 함. 5번(중간 인간 체크포인트)과 지점은 같지만(phase boundary)
방향이 다름 — 5번은 사람 개입, 이건 무인 자기보정. 둘을 같은 훅에 얹을 수
있는지 착수 시 확인.

**게이트 (관측):** 다음 멀티-phase dogfood의 journal.md에서 — 후반 phase의
stall/재시도/re-plan이 초반 phase 대비 유의미하게 몰리는지, re-plan 사유가
"선행 phase 결과와 불일치" 계열인지 확인. 그 패턴이 관측되기 전에는 착수
않는다 (2번 진단과 같은 저널을 보므로 함께 조사하면 싸다).

**게이트 확인 (2026-07-06, Lane C 런):** 미관측 — 전 14태스크 첫 시도
PASS, 후반 phase 몰림 없음. 오히려 2.5→2.6 재사용 계약 메모가 phase 내
신선도 문제를 저널 경유로 흡수한 반례 관측. 게이트 유지.

**계측 착수 (2026-07-06):** 게이트는 유지하되 관측 장비만 먼저 싣는다 —
Lane C는 phase 2개짜리 런이라 "미관측"은 반증이 아니라 검정력 부족
(실패 모드의 표적은 phase 4-5). 템플릿 C에 NEXT PHASE 입력 + plan 신선도
체크(advisory, FAIL 불가·재분해 제안 금지) + `freshness-note` 필드 추가,
3번 structure-note와 같은 패턴. 오케스트레이터는 노트를 journal
`[phase N] verified` 엔트리에 verbatim 병기하고 handoff "Watch out for"로
이월 — 의심이 실재하면 해당 태스크의 implementer가 부딪히고 기존
blocked/stall 경로가 처리한다 (Lane C에서 관측된 저널 경유 흡수와 같은
메커니즘). plan.md 불변·re-plan 경로 유일 원칙 무손상. 6번 supervisor와는
관측 주체로 비결합(supervisor의 루프 단위는 프로세스 수명이지 phase
경계가 아님) — 단 grep 가능한 라인 포맷이라 6번 착수 시 알림 요약으로
물릴 수 있음. **승격/클로즈 기준:** 다음 멀티-phase dogfood에서
freshness-note가 실제 stall·재작업과 상관되어 쌓이면 1안(조기 re-plan
발동)으로 승격, 수 런에 걸쳐 비거나 소음이면 8번 클로즈.

## 10. loopnext — run 사이 스펙 버전업 반복 (2026-07-08 신규)

**근거 (생명주기 공백 — 관측 게이트 비적용):** 얼어붙은 스펙은 run
하나로는 폭포수다. 사람은 백지 명세는 못해도 존재하는 물건 비판은
잘하므로, MVP는 스펙 발견 장치가 된다. 그런데 완료된 run 위에 다음
run을 얹는 경로가 미정의 — loopspec 가드는 "archive or abort"를 묻지만
archive 절차 자체가 state-format에 없고, 3번이 심은 structure-note
advisory는 소비처가 없다. 실전 프로젝트를 dogfood하면 run 2 수요는
100% 발생하므로, 하드닝이 아니라 공백 — 관측을 기다릴 이유가 약하다.

**설계 (확정, 2026-07-08):** `docs/superpowers/specs/
2026-07-08-loopnext-design.md`. 핵심 원칙: **spec은 run 안에서 얼고,
run 사이에서 버전업된다.** `/loopnext` = 완료 run과 다음 run 사이의
인간 touchpoint — 사용 피드백 + 저널 advisory(structure-note/
